Scope: factual audit of existing Auth.js providers, identity persistence, session, account/logout, email authentication, and Auth-specific runtime behavior. No application, Auth, schema, migration, dependency, or secret value was changed or exposed.

## Audit boundary

The audited implementation is `next-auth` `5.0.0-beta.25` from `package.json`, instantiated in `src/auth/index.ts` with `authOptions` from `src/auth/config.ts`. It uses no Auth.js Adapter and declares no `session`, `jwt`, `cookies`, or `trustHost` option in `authOptions`. The only persistence code found is the custom `users` model/service path described below. A database `sessions`, `accounts`, or verification-token table is absent from the AUD-020 schema inventory.

The audit was conducted at `503ca9a0f46bc732fe974b6d336e1d1fcd2eb8a4` on `audit/kyd-starter-v1`. The visible untracked Runtime/bootstrap pack predates this task; no application implementation file had a Git diff.

## 2. Auth.js callbacks and Google OAuth

- `src/app/api/auth/[...nextauth]/route.ts` exposes Auth.js `GET` and `POST` handlers exported by `NextAuth(authOptions)`.
- The `signIn` callback always returns `true`; it does not inspect the provided `user`, `account`, `profile`, `email`, or `credentials` values.
- Google OAuth uses provider defaults: no custom scopes or profile mapping are configured. `handleSignInUser` receives Auth.js `user` and `account`, but the configured callback does not use `profile` to assert a Google verified-email claim.
- On the first JWT callback invocation with both `user` and `account`, `handleSignInUser` constructs a custom user record from `user.email`, `user.name`, `user.image`, `account.type`, `account.provider`, and `account.providerAccountId`. It then calls `saveUser` and stores only internal display/identity fields in `token.user`.
- The `jwt` callback catches persistence errors, logs them, and returns the prior token. No custom Auth error page or typed recovery path is configured. This can leave the session callback without the expected custom `token.user` payload; runtime behavior is not tested.
- `redirect` accepts relative paths and same-origin absolute URLs, otherwise returns `baseUrl`. This is the only Auth.js callback URL allowlist. The custom sign-in page separately reads `callbackUrl` and passes it directly to `next/navigation` `redirect` when a session already exists; that code path has no local validation and requires a targeted redirect-safety test.

## 4. Session model and logout

- `src/auth/session.tsx` conditionally mounts `SessionProvider` only when `isAuthEnabled()` is true. The locale layout mounts it around `AppContextProvider` and the application tree.
- `src/auth/config.ts`'s session callback replaces `session.user` with `token.user` when present. `src/types/next-auth.d.ts` augments JWT/session user data with `uuid`, `nickname`, `avatar_url`, and `created_at`; default session user fields retain email/name/image.
- There is no Adapter, session table, or explicit database-session code. The configuration contains no explicit session expiry, refresh, update, cookie, or JWT options. The exact production cookie/session lifetime is `UNKNOWN / NOT VERIFIED` from repository evidence; it should be treated as the Auth.js default path pending runtime verification.
- `getUserUuid()` calls `auth()` server-side and uses `session.user.uuid`; `getUserInfo()` loads the canonical database user by that UUID. The client `AppContextProvider` calls `/api/get-user-info` when a session exists and retains the returned database user in React state.
- Logout controls in `src/components/sign/user.tsx` and `src/components/dashboard/sidebar/user.tsx` call `next-auth/react` `signOut()` with no custom redirect or cleanup. There is no custom signout handler. Actual cookie invalidation and post-logout redirect are `UNKNOWN / NOT VERIFIED` without an integration test.

## 5. Canonical user and trusted same-email identity

- The canonical business identity is `users.uuid`: it is unique in `src/db/schema.ts`, added to `token.user`, and referenced by orders, credits, API keys, affiliates, feedback, and protected API/page logic as `user_uuid`. Email is also copied into orders and used for selected lookups.
- `users.id` is an identity primary key. `email` is `NOT NULL` but not globally unique; the sole email constraint is `email_provider_unique_idx` over `(email, signin_provider)`. The schema permits multiple rows for the same email when provider values differ.
- Provider data lives only on the `users` row as `signin_type`, `signin_provider`, and `signin_openid`; there is no account-link table and no representation for multiple provider account IDs on one user.
- `saveUser` calls `findUserByEmail(email)` without provider filtering. Sequential sign-in for an existing email returns the first existing row and does not update provider fields. Therefore, if a future trusted Magic Link path reaches `saveUser` with the same email as a prior Google user, static evidence indicates it would reuse that row's `uuid` rather than insert another row.
- This is not a complete trusted-provider policy: the present code does not enforce verified email in the Google OAuth callback, the One Tap path accepts any token-info payload containing email, and the database does not globally constrain concurrent same-email inserts. It also does not record the second provider association on an existing row.

### Required scenario: Google then Magic Link

1. Google OAuth with `user@example.com` would call `handleSignInUser` and `saveUser`; absent an existing email, it creates a `users` row and stores its UUID in the JWT.
2. A real Email Magic Link path does not exist, so the requested second step cannot occur today.
3. If a future trusted Email provider invokes the existing `saveUser` function with `user@example.com`, its email-first lookup would return the Google-created row, yielding the same canonical UUID in the normal sequential case.

**Conclusion: `YES — PATCH`.** The reusable email-first canonical identity path avoids a mandated Adapter/schema refactor, but V1 needs a bounded patch to add the actual Magic Link flow, accept only trusted verified identities, ensure deterministic same-email creation/linking (including concurrency), and add tests. `KEEP`, `KEEP + TEST`, and `WRAP` alone cannot supply the absent Magic Link behavior or enforce the frozen trust policy. `REFACTOR` is not justified because the existing callback/user/session boundary can remain.

## 6. Account, profile, logout, and protected routes

- Console protection is implemented by `src/app/[locale]/(default)/(console)/layout.tsx`, which requires `getUserInfo()` and redirects unauthenticated/missing users to `/auth/signin`. The admin layout performs the same user lookup, then checks `ADMIN_EMAILS` and renders an `Empty` no-access state for non-members.
- Selected console pages additionally check `getUserUuid()` and redirect with a `callbackUrl` composed from `NEXT_PUBLIC_WEB_URL`. Authenticated APIs such as `/api/get-user-info`, `/api/get-user-credits`, `/api/update-invite-code`, `/api/ping`, and checkout use `getUserUuid()`.
- The global middleware is locale middleware only; it does not enforce Auth. Route protection is consequently layout/page/API specific.
- Account UI consists of avatar/name/email display, a `my-orders` user-center link, console/admin navigation, and sign-out controls. No dedicated editable profile route was found. No account deletion behavior was found.
- The account shell and logout controls are reusable. A V1 profile surface remains a bounded `PATCH` concern; it does not require account deletion or an Auth schema redesign.

## 7. Other auth paths and security observations

- GitHub OAuth shares the same `handleSignInUser`/`saveUser` flow. It is default-disabled and not a V1 target, so retention as `KEEP-DISABLED` is preferred over deletion. Its trusted-email semantics are not verified.
- Google One Tap's `authorize` function calls Google's `tokeninfo` endpoint and maps `email`, `sub`, name, and image to a credential user. It checks only that a configured client ID exists; it does not compare a returned audience to that client ID, and it accepts an email even when the returned `email_verified` is false (it only sets `emailVerified` on the returned object). These are code facts, not a claim of a completed exploit.
- `useOneTapLogin` logs the provider response and the `signIn` result, and schedules another One Tap prompt every three seconds while unauthenticated. This is an Auth-specific token exposure/abuse observation. As the feature is off by default, `KEEP-DISABLED` is the safe current disposition; any production enablement requires a dedicated security test and minimal patch.
- No Auth-specific rate limiter, Magic Link request throttle, email enumeration control, or explicit cookie configuration was found. Broad logging/redaction, rate limiting, and secret hygiene remain for `AUD-070`.
- `.env.example` contains Auth variable names and a non-empty example `AUTH_SECRET` value. This audit does not reproduce it; the example value must not be treated as an operational secret. Auth enablement and provider IDs are intentionally public-prefixed where used by the client; provider secrets retain non-public names.
